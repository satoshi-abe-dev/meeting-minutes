# 新機能の起票〜実装完了

引数（`$ARGUMENTS`）で渡された機能の依頼を、以下の手順で最後まで進める。

## 1. 内容を理解する・必要なら確認する

- 依頼が具体的で設計上の曖昧さが無ければ、そのまま2へ進む
- 設計判断が必要（複数の実装方針がある、UIの見た目が絡む、スコープが不明確等）な場合は、
  `AskUserQuestion` で先に確認する。中身が固まってから起票する
- 既存のコードベース（`src/meeting_minutes/`, `gui.py`, `cli.py` 等）を確認し、
  関連する既存の仕組み（設定の優先順位、フォールバック方針、トークン予算の考え方等）と
  矛盾しないか、流用できる既存関数が無いか確認する

## 2. GitHub Issueを起票する

`gh issue create` で以下の構成のIssueを作る（過去のIssue #16, #21, #34等のパターンに
倣う）：

- タイトル：機能を一言で
- 背景：なぜ必要か
- 方針：具体的な設計判断（設定項目名、優先順位、フォールバック条件など）
- 完了条件：テストでカバーすべき点、ドキュメント更新の要否

ラベルは `enhancement` + 優先度（`priority:P1`/`priority:P2`）を付ける。

## 3. workerに依頼する

`SendMessage` で `meeting-minutes-worker` 宛に、Issueへのリンクと要点をまとめて送る。
規模が大きい場合は、workerから実装方針の確認が返ってくることがあるので、それには
manager（このセッション）の判断で妥当なら承認して進めてもらう（大きな設計変更でなければ
都度ユーザーに確認を取り直す必要はない）。

## 4. PRが届くたびにレビューする

`.claude/skills/review-worker-pr/SKILL.md` と同じ手順（機密チェック・差分確認・
独自pytest・Codex独立レビュー）で確認する。問題があれば具体的に指摘して差し戻し、
修正版が届いたら再度レビューする。この往復は何度でも繰り返す（実績：1機能で6ラウンド
かかったこともある）。

## 5. マージしてIssueをクローズする

全て問題なければマージし、workerに報告した上で、`gh issue close` で対応内容を
要約してクローズする。

## 6. 最後にユーザーに報告する

Issue番号・関連PR番号・実装の要点をまとめてユーザーに報告する。
