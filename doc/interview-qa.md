# 想定問答集

このプロジェクトについて聞かれそうな質問と、答え方のメモ。
各回答は「結論 → 理由 → トレードオフ／代替案」の順。設計の詳細は [`DESIGN.md`](DESIGN.md)。

---

### Q. どんなツール？ 一言で

A. 打ち合わせの録画動画を渡すと、文字起こし・画面キャプチャの解析・議事録生成までを
**すべてローカルで**行って Markdown の議事録を返す CLI / GUI ツール。外部にデータを
送らないことが目的。

---

### Q. なぜローカル LLM？ クラウド API ではダメだったのか

A. 想定ユーザーが、会議に顧客情報・未公開情報・個人情報を含み、**録音を外部送信できない**
現場だから。NDA や社内規程で、そもそもクラウド STT / 生成 AI の利用が審査を通らない。

- ここでは「外に出ないこと」が機能要件。精度が多少落ちても成立する。
- 代替案としてクラウド版も作れるが、それは別プロダクト。1 つのコードで両対応にすると
  「うっかり送信」の事故リスクを抱えるので、ローカル専用に振り切った。

---

### Q. `Deps` による DI は大げさでは？ もっと素朴に書けたのでは

A. 目的は 1 つ、**ffmpeg とローカル LLM サーバーを用意せずにパイプラインをテストする**こと。

- `pipeline.run()` は工程の順序・進捗通知・`output/<動画名>/` の組み立てを担う。ここを
  実物の ffmpeg / LLM 込みでしかテストできないと、CI に載らず失敗の切り分けも難しい。
- `Deps` は関数フィールドを持つ dataclass だけで、クラス階層は作っていない。抽象基底
  クラス＋サブクラスは工程が関数 1 個で足りる現状ではオーバースペックと判断した。
- 副産物として、`transcribe_wav` を差し替えれば mlx-whisper への乗り換えもできる。

---

### Q. 1 時間の会議の音声はどう捌く？ メモリは？

A. 文字起こしはストリーミングで、セグメントが確定するたびに進捗を返す。議事録生成は
**文字起こしが長い場合 map-reduce に切り替える**（チャンク要約 → 統合）。

- 丸ごと LLM に渡すとコンテキスト超過で切り詰められ、決定事項を取りこぼす。
- メモリの主な消費はモデル本体。faster-whisper の `large-v3` で数 GB、ローカル LLM は
  量子化 7〜8B で 8〜12GB 目安（→ [`models.md`](models.md)）。LM Studio の
  Just-in-time loading を使えば LLM と VLM を必要なときだけ入れ替えられる。
- トレードオフ：チャンク要約は LLM 呼び出しが増えて遅くなり、細部が落ちることがある。

### Q. LM Studio が起動していなかったら？ 途中で失敗したら？

A. 2 段構えにした。実体験がきっかけ：文字起こしに数分かけたあと、フレーム解析で
LM Studio が「No models loaded」を返して全部やり直しになった。

- **起動前チェック（preflight）**：音声抽出より前に、設定した LLM / VLM モデルへ
  極小リクエストを投げて疎通確認する。落ちるならここで即中断＝数分待つ前に気づける。
- **エラーメッセージ**：接続失敗は `LLMConnectionError` に集約。400 応答に
  `No models loaded` 等があれば「JIT を ON / Loaded Instances でロード / モデル名を
  Library と一致」のヒントを添える。GUI はダイアログ＋ログ。
- **途中再開**：再実行時は `transcript/transcript.json` / `frames/frames.json` / `frames/frame_notes.json`
  （フレーム解析、1枚単位）/ `minutes_partials.json`（チャンク要約、1つ単位）を
  すべて再利用し、終わっている分はやり直さない。議事録の最終統合だけがタイムアウト
  した事例をきっかけにチャンク要約側の永続化を足し、そのあと「60枚のフレーム解析を
  毎回やり直す方が無駄」と気づいて frame_notes 側も同じ方式に揃えた。最初から
  やり直すなら `--fresh` / GUI のチェックボックス。
- フレーム解析は **1 枚の失敗は握りつぶして続行**。接続自体が死んでいる場合は中断。

### Q. 文字起こしは何を使っている？ なぜ 2 つ持っている？

A. `transcribe.py` が 2 バックエンドを持ち、`config.backend` で選ぶ。既定 `auto`。

- **faster-whisper（CTranslate2）** — どの OS でも動き、日本語精度も実用的。ただし
  Apple Silicon の GPU を使えず Mac では CPU 実行で遅い（`large-v3` で 1 時間会議に
  数十分〜1 時間）。
- **mlx-whisper** — Apple GPU を使い Mac では大幅に速い。Apple Silicon 以外では
  pip が入れない（環境マーカー）。
- Whisper API（クラウド）は「外部送信しない」という前提に反するので不採用。
- 実装のポイント：`transcribe_wav()` のシグネチャは変えず、内部で
  `resolve_backend()` の結果に応じて実装を切り替えた。`pipeline.Deps` も既存テストも
  無変更で済んだ。
- 割り切り：mlx-whisper は結果を一括で返すので、文字起こし中の進捗が出せない
  （バーは 0→100 に飛ぶ）。逐次表示には音声の自前チャンク分割が要り、そこは後回し。

### Q. モデル（数 GB）はどう配る？ 利用者に毎回ダウンロードさせるのか

A. モデルはリポジトリに含めず、HuggingFace の共有キャッシュ（`~/.cache/huggingface/hub/`）に
置く。**利用者ごとに 1 台につき一度だけ**ダウンロードが要る。

- 手間を増やさないため、`scripts/setup.sh` が venv 作成・依存導入に続けて
  `python prefetch.py` を呼び、**セットアップの 1 コマンドの中で**モデルまで取得する。
  利用者が別途打つコマンドは無い。
- `prefetch` は `resolve_backend()` の結果に合うモデルだけを落とし、取得済みなら
  何もしない（冪等）。
- setup.sh を通さず直接動かした人向けの保険として、文字起こし本体の前に
  「未取得なら初回ダウンロード」を GUI ログに 1 行出す（フリーズに見えないように）。
- モデルをリポジトリに同梱しない理由：1.6GB を Git に載せるのは不可。Git LFS も
  導入の手間が増える。DL は初回だけでオフライン運用に移れるので、そこは受け入れた。
- エアギャップ環境では `HF_HOME` を社内ミラーに向けるか、キャッシュを配布物に含める。

### Q. フレーム抽出のしきい値はどう決めた？ 撮りすぎ／取りこぼしは

A. 「シーン変化（`select='gt(scene,TH)'`）」と「一定間隔（前回選択から N 秒経過）」の
**OR** で 1 パス抽出し、その後に間引く。

- 動きの少ない会議で間隔だけだとスライド送りを逃す。シーン変化だけだとカメラ揺れや
  カーソル移動で撮りすぎる。両方を足して補完し合う。
- 後処理で「近接フレームの間引き（`min_gap_sec`）」と「上限（`max_frames`）で等間隔に
  絞る」を掛け、VLM 呼び出し回数に歯止めをかける。
- 値（`interval_sec` / `scene_threshold` / `max_frames`）は `config.toml` で調整可能。
  既定は短い会議で試した経験値。

### Q. ffmpeg はどう呼んでいる？ ライブラリは使わないの？

A. `subprocess` で ffmpeg / ffprobe を直接呼ぶ薄いラッパ（`ffmpeg_utils.py`）。

- `ffmpeg-python` 等のバインディングは、結局 CLI 引数を組むだけなので依存を足す価値が
  薄い。存在チェック・終了コード・stderr の要約だけ自前で持てば十分。
- 実話：ffmpeg 9.0 で `-vsync` が廃止され、フレーム抽出が壊れた。後継の
  `-fps_mode vfr` に直し、生成クリップでの統合テストを追加して回帰を防いだ。

### Q. このコードで一番自信がないところは

A. 2 つ。

1. **エラー回復** — 起動前チェックと途中再開（transcript / frames / frame_notes /
   チャンク要約すべて再利用）は入れたが、LLM 落ち時の自動リトライはまだ。
2. **プロンプトの作り込み** — 議事録テンプレは用意したが、良い出力／悪い出力を並べた
   評価はまだ。モデル差の検証も浅い。

（正直に弱点を言い、次の一手をセットで話す。）

### Q. テストは何を担保している？

A. 純粋ロジック（フレーム間引き、チャンク分割、設定の優先順位解決）は単体テスト。
パイプラインは `Deps` にフェイクを注入して「工程順序・進捗・出力パス」を検証。
ffmpeg がある環境では、生成クリップから実際にフレームを抜く統合テストも走る。
ローカル LLM を要するテストはスタブで置き換えている。

---

### Q. 次に手を入れるなら？ なぜ今やっていない？

A. 優先順で：

1. CI（GitHub Actions で pytest）と lint/型チェック（ruff / pyright）
2. LLM 落ち時の自動リトライ
3. 出力品質の簡易評価（良い例／悪い例）
4. 話者分離、GUI からの設定編集

今やっていないのは、まず「実データで一度通す」ことを優先したから。動作実績を取ってから
堅牢化に入る順序にした。

## 30 秒で説明する版

> 打ち合わせの録画から議事録を自動生成するツールです。特徴は、文字起こしから要約まで
> 全部ローカルで完結して、録音データを一切外に出さないこと。会議に顧客情報や未公開情報が
> 含まれてクラウド AI に乗せられない、という現場を想定しています。構成は、ffmpeg で
> 音声とフレームを取り出し、Whisper（Apple GPU の mlx か faster-whisper）で文字起こし、
> ローカルの LLM / VLM で画面内容の要点化と議事録生成、というパイプラインです。GUI・CLI・
> テストが同じ 1 つの関数を呼ぶ形にして、各工程を差し替え可能にしてあるので、ffmpeg や
> LLM が無くてもパイプラインのテストができます。長時間処理なので、処理前に LLM の疎通を
> 確認して早く失敗させ、失敗しても文字起こしからはやり直さない（中間結果を再利用）よう
> にしています。次の課題は CI と出力品質の評価です。
