# 実験: おまかせフォーマット生成の CrewAI 版

日本語 | [English](crewai_experiment_en.md)

## まとめ

**試したこと。** おまかせモードの型の生成に、CrewAI を使った 2 つ目のエンジン（判定・調査・設計の
3 エージェント）を、開発者用の引数の裏で実際のパイプラインに組み込んだ（Issue #192）。

**分かったこと。** テストで使う偽物ではなく、本物のパッケージを動かし、また読むと、偽物では見えない
ことが分かった。

1. タスクごとの出力（エージェントに渡した材料の全体を含む）が、ホームディレクトリ下の
   データベース、つまり `output/` の外に保存される。
2. import するだけで、ホームにファイルが作られる。
3. `max_execution_time` は動いているエージェントを止めず、そのエラーには材料の全文が引用される。
4. コンテキストが超過すると、手順数の上限の外で、追加の LLM 呼び出しで要約する。計算しただけの
   呼び出し回数の上限は、上限になっていない。
5. エージェントが LLM を共有すると、利用量のメトリクスが重複して数えられる（3 リクエストが 9）。
6. こちらのクリーンアップのコードのバグ（Windows で Ctrl+C を送る）が、3 つ目の OS の CI で見つかった。

これらは、**ハーネス**（エージェントの外側から動きを制御・制限するコード。テスト用のハーネスではない）と、
別ベンダー（Codex）および manager セッションのレビューで塞いだ。レビューでは、差し替えに失敗しても
黙って続行する実装と、強制されていなかった上の 2 つの上限（3・4）が見つかった。どの修正にもテストが
あり、一部は本物の CrewAI に対するもの。

**比べたこと。** 会議 2 件・ローカルモデル 1 つで、CrewAI 版は、単発とほぼ同じ時間、4 倍の LLM 呼び出しで、
粗い型を作った。2 件に共通して明確に良い点はなかった。

**判断。** ユーザーには推奨せず、採用しない。既定では使われず、開発者用の引数でだけ選べる。コードは
実験の記録として残す。

**やらなかったこと。** Issue が求めた、Wi-Fi をオフにしたパイプライン全体の実行は、ユーザー向けでなくなった
ので実施しない。代わりに、本物の CrewAI を偽のローカルサーバーにつないで、loopback への接続だけだったことを
確認した。

以降は、再現したい、あるいは詳細を読みたい開発者向け。ツールの既定の動作は変わらず、ここに書いたものは何も
入れなくてもツールは使える。

## 何をするものか

おまかせモードの型（見出し構成）は、通常 **LLM の 1 回の呼び出し**（`minutes.py` の
`_generate_structure`）で作る。この実験では [CrewAI](https://docs.crewai.com/) の 3 エージェントで分担した。

1. **判定役**: 資料から会議の種類を判定する。
2. **調査役**: 検索ツールで資料を調べる（数値・期限・担当者・宿題があるか）。
3. **設計役**: 2 つの結果から型を作る。ルールは単発版と同じ（`prompts/structure_ja.txt`）。

目的は、CrewAI を本来の形（エージェントが見る場所を判断する）で試し、同じ入力での単発版との比較を残すこと。
単発版と同等か、それより悪い結果でも、成果として扱う。

## ハーネスが制限していること

エージェントは進め方を決め、できないことはハーネスが決める。README の「開発体制」のハーネス
エンジニアリングと同じ考え方を、開発の作業ではなくエージェントに当てはめたもの。各項目にテストがある。
実装は `src/meeting_minutes/model/structure_crewai.py`。

1. **ローカルに留める。** CrewAI を import する前に、テレメトリとトレースを切る
   （`CREWAI_DISABLE_TELEMETRY`・`OTEL_SDK_DISABLED`・`CREWAI_DISABLE_TRACKING`=true、
   `CREWAI_TRACING_ENABLED`=false）。エージェントは `[ai] base_url` のサーバーとだけ、設定したキーと
   モデルで通信し、環境変数経由でクラウドの接続先に切り替わることはない。
2. **材料を残さない。** CrewAI が持つ材料の写し（データディレクトリ下の SQLite）を、専用の一時フォルダー
   （macOS・Linux は権限 0700、Windows は `%TEMP%` の権限を引き継ぐ）へ向け、実行が終わった直後に削除する
   （エラーや割り込みでも同じ）。強制終了されたプロセスの残りは次回起動時に削除する。差し替えを設定
   できない、または確認できない場合は、**実行を拒否**する。
3. **手順と呼び出しを制限する。** `max_iter` は判定役・調査役・設計役で 2 / 4 / 2、検索ツールは合計 6 回、
   **LLM 呼び出しは合計 22 回まで強制**（3 エージェントが共有するカウンターで、要約も含め全部数える。
   通常は 4 回）。23 回目は拒否し、内蔵の型にフォールバックする。コンテキスト超過時の CrewAI の自動要約は
   切ってあり、超過したら追加の呼び出しをせず失敗する。
4. **結果を単発版と同じに扱う。** 同じチェック（必須プレースホルダー・サイズ）と、内蔵の型への同じ
   フォールバック。エラーメッセージは、材料を引用するものがあるので短くして表示する。

**ハーネスがしないこと。**

- 実時間の上限はない。各呼び出しは `[ai] timeout`（既定 600 秒）で区切られるだけで（OpenAI クライアントが、
  失敗した HTTP リクエストを 1 回の呼び出しの中で最大 2 回リトライしうるが、カウンターには見えない）、
  CrewAI 自身の `max_execution_time` は、効かないので使っていない。
- 「中止」ボタンは、エージェントの実行を途中で止めない。作業が終わった時点で効く（比較では 1〜2 分程度）。
- 実行中の強制終了（SIGKILL・クラッシュ・停電）では、一時フォルダー（`$TMPDIR` / `%TEMP%`、あなた自身の
  アカウント配下）が、次回起動か OS の掃除まで残る。
- CrewAI を import すると `~/.config/crewai` などが作られる。会議の内容は含まない。

## 再現する（開発者向け）

CrewAI は **Python 3.10〜3.13 のみ**対応（3.14 は非対応）。別の仮想環境に入れる（`.venv*/` は git 管理外）。

```sh
python3.13 -m venv .venv-py313
.venv-py313/bin/python -m pip install -r requirements-dev.txt -r requirements-agent.txt
.venv-py313/bin/python src/meeting_minutes/gui.py --structure-engine crewai   # 「おまかせ」を選ぶ
```

引数なしなら動作は変わらない。引数を付けて CrewAI が未インストールなら、起動時にインストール方法を示して
終了する（スタックトレースなし）。2 つのエンジンの比較は次のとおり。

```sh
.venv-py313/bin/python scripts/compare_structure_engines.py output/<会議のフォルダー>
```

`transcript.json` のあるフォルダーを使う。両エンジンには、既存の処理で作った**同じ材料**を渡し、型の生成直後に
止まる（議事録は作らない）。結果は `output/_compare/`（git 管理外）に、表（`comparison.md`）・機械可読版・
材料そのもの・型として保存される。自動の採点はない。比較は、ローカルサーバーに対して **1 回ずつ**実行する
（下記）。

## 比較の結果

会議 2 件（A・B）、ローカルモデル 1 つ（`qwen2.5-coder-32b-instruct-mlx`、LM Studio 経由）、議事録の言語は
英語、エンジンごと・会議ごとに成功した実行が 1 回。会議の内容はここに書かない。両エンジンには同じ材料を渡した
（ハッシュで確認）。

| | A: 単発 | A: CrewAI | B: 単発 | B: CrewAI |
| --- | --- | --- | --- | --- |
| 材料 | チャンク要約・約 7,100 字 | 同左 | 文字起こし全文・約 22,700 字 | 同左 |
| チェックを通った | はい | はい | はい | はい |
| 実時間 | 49 秒 | 50 秒 | 90 秒 | 92 秒 |
| LLM 呼び出し | 1 | 4 | 1 | 4 |
| 検索ツール（上限 6） | 0 | 4 | 0 | 4 |
| 節の数 | 12 | 7 | 12 | 6 |

1. **粒度。** 単発は約 2 倍の節で話題を細かく分けた。CrewAI は話題をまとめ、2 件とも、独立した節を持てない
   内容があった。
2. **固有の情報（一貫した傾向なし）。** 別の録画に使い回せる型が狙い。A では CrewAI の指示文に行事名と年が入り、
   B では単発の指示文にウェブサイトや製品の名前が入った。どちらが使い回しやすいとも言えない。
3. **時間と呼び出し。** 時間は数秒の差、CrewAI の LLM 呼び出しは 4 倍。調査役はツールを 4 回使い、上限 6 の
   範囲内だった。

会議 2 件・モデル 1 つ・各 1 回（サンプリングは決定的でない）なので、勝ち負けは言えない。単純な単発版を
既定のまま残す。品質を言うには、より多くの会議が必要。

**比較は 1 回ずつ実行すること。** 誤って同じ LM Studio のモデルに 2 つの比較を同時に起動したところ、リクエストが
重なっている間に MLX バックエンドがクラッシュし、重なった 2 つのリクエストが同時に失敗した（単独のものは成功）。
CrewAI エンジンは失敗を報告し、内蔵の型にフォールバックする経路に入った。上の数値は、単独で動いた
リクエストのものだけで、B はこのため、2 つのエンジンが別々の実行から来ている。
