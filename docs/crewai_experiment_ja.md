# 実験: おまかせフォーマット生成の CrewAI 版

日本語 | [English](crewai_experiment_en.md)

## まとめ

**ユーザーには推奨せず、採用しない。**
試した結果、副作用への対策が要り、単発版より良くもならなかった。
コードは実験の記録として残し、開発者用の引数でだけ使える。

### 試したこと

1. おまかせモードの型の生成に、CrewAI を使った 2 つ目のエンジン（判定・調査・設計の 3 エージェント）を追加した（Issue #192）。
2. 開発者用の引数の裏で、実際のパイプラインに組み込んだ。

### 分かったこと

テストで使う偽物ではなく、本物のパッケージを動かし、また読むと、偽物では見えないことが分かった。

1. タスクごとの出力（エージェントに渡した材料の全体を含む）が、ホームディレクトリ下のデータベース、つまり `output/` の外に保存される。
2. import するだけで、ホームにファイルが作られる。
3. `max_execution_time` は動いているエージェントを止めず、そのエラーには材料の全文が引用される。
4. コンテキストが超過すると、手順数の上限の外で、追加の LLM 呼び出しで要約する。計算しただけの呼び出し回数の上限は、上限になっていない。
5. エージェントが LLM を共有すると、利用量のメトリクスが重複して数えられる（3 リクエストが 9）。
6. こちらのクリーンアップのコードのバグ（Windows で Ctrl+C を送る）が、3 つ目の OS の CI で見つかった。

### 塞いだ方法

1. **ハーネス**（エージェントの外側から動きを制御・制限するコード。テスト用のハーネスではない）。
2. 別ベンダー（Codex）と manager セッションのレビュー。差し替えに失敗しても黙って続行する実装と、強制されていなかった上限（3・4）を見つけた。
3. 3 つの OS の CI。Windows のバグ（6）を見つけた。

どの修正にもテストがあり、一部は本物の CrewAI に対するもの。

### 比べた結果

会議 2 件・ローカルモデル 1 つで、CrewAI 版は次のとおりだった。

1. 時間: 単発とほぼ同じ。
2. LLM 呼び出し: 4 倍。
3. 型: 粗い。

2 件に共通して明確に良い点はなかった。

### 判断

1. ユーザーには推奨せず、採用しない。
2. 既定では使われず、開発者用の引数でだけ選べる。
3. コードは実験の記録として残す。

### やらなかったこと

1. Issue が求めた、Wi-Fi をオフにしたパイプライン全体の実行は、ユーザー向けでなくなったので実施しない。
2. 代わりに、本物の CrewAI を偽のローカルサーバーにつないで、loopback への接続だけだったことを確認した。

以降は、再現したい、あるいは詳細を読みたい開発者向け。
ツールの既定の動作は変わらず、ここに書いたものは何も入れなくてもツールは使える。

## 何をするものか

おまかせモードの型（見出し構成）は、通常 **LLM の 1 回の呼び出し**（`minutes.py` の `_generate_structure`）で作る。
この実験では [CrewAI](https://docs.crewai.com/) の 3 エージェントで分担した。

1. **判定役**: 資料から会議の種類を判定する。
2. **調査役**: 検索ツールで資料を調べる（数値・期限・担当者・宿題があるか）。
3. **設計役**: 2 つの結果から型を作る。ルールは単発版と同じ（`prompts/structure_ja.txt`）。

目的は、CrewAI を本来の形（エージェントが見る場所を判断する）で試し、同じ入力での単発版との比較を残すこと。
単発版と同等か、それより悪い結果でも、成果として扱う。

## ハーネスが制限していること

エージェントは進め方を決め、できないことはハーネスが決める。
README の「開発体制」のハーネスエンジニアリングと同じ考え方を、開発の作業ではなくエージェントに当てはめたもの。
各項目にテストがある。実装は `src/meeting_minutes/model/structure_crewai.py`。

### 1. ローカルに留める

1. CrewAI を import する前に、テレメトリとトレースを切る。
   `CREWAI_DISABLE_TELEMETRY`・`OTEL_SDK_DISABLED`・`CREWAI_DISABLE_TRACKING` を true に、`CREWAI_TRACING_ENABLED` を false にする。
2. エージェントは `[ai] base_url` のサーバーとだけ、設定したキーとモデルで通信する。
3. 環境変数経由でクラウドの接続先に切り替わることはない。

### 2. 材料を残さない

CrewAI は、材料の写しを SQLite に保存する。

1. 保存先を、専用の一時フォルダーへ向ける（macOS・Linux は権限 0700、Windows は `%TEMP%` の権限を引き継ぐ）。
2. 実行が終わった直後に削除する（エラーや割り込みで終わった場合も）。
3. 強制終了されたプロセスの残りは、次回起動時に削除する。
4. 差し替えを設定できない、または確認できない場合は、**実行を拒否**する。

### 3. 手順と呼び出しを制限する

1. `max_iter`: 判定役 2・調査役 4・設計役 2。
2. 検索ツール: 合計 6 回。
3. LLM 呼び出し: **合計 22 回まで強制**。3 エージェントが共有するカウンターで、要約も含め全部数える（通常は 4 回）。
4. 23 回目は拒否して、内蔵の型にフォールバックする。
5. コンテキスト超過時の自動要約は切ってある。超過したら、追加の呼び出しをせず失敗する。

### 4. 結果を単発版と同じに扱う

1. 同じチェック（必須プレースホルダー・サイズ）。
2. 同じフォールバック（内蔵の型）。
3. エラーメッセージは、材料を引用するものがあるので、短くして表示する。

### ハーネスがしないこと

1. **実時間の上限はない。** 各呼び出しは `[ai] timeout`（既定 600 秒）で区切られるだけ。
2. OpenAI クライアントは、失敗した HTTP リクエストを 1 回の呼び出しの中で最大 2 回リトライしうる。カウンターには見えない。
3. CrewAI 自身の `max_execution_time` は、効かないので使っていない。
4. 「中止」ボタンは、エージェントを途中で止めない。終わった時点で効く（比較では 1〜2 分程度）。
5. 実行中の強制終了（SIGKILL・クラッシュ・停電）では、一時フォルダーが、次回起動か OS の掃除まで残る（`$TMPDIR` / `%TEMP%`、あなた自身のアカウント配下）。
6. CrewAI を import すると、`~/.config/crewai` などが作られる（会議の内容は含まない）。

## 再現する（開発者向け）

CrewAI は **Python 3.10〜3.13 のみ**対応する（3.14 は非対応）。別の仮想環境に入れる（`.venv*/` は git 管理外）。

### 1. 環境を作る

```sh
python3.13 -m venv .venv-py313
.venv-py313/bin/python -m pip install -r requirements-dev.txt -r requirements-agent.txt
```

### 2. 起動する

```sh
.venv-py313/bin/python src/meeting_minutes/gui.py --structure-engine crewai
```

1. 議事録フォーマットで「おまかせ」を選ぶ。
2. 引数なしなら、動作は変わらない。
3. 引数を付けて CrewAI が未インストールなら、起動時にインストール方法を示して終了する（スタックトレースなし）。

### 3. 2 つのエンジンを比較する

```sh
.venv-py313/bin/python scripts/compare_structure_engines.py output/<会議のフォルダー>
```

1. `transcript.json` のあるフォルダーを使う。
2. 両エンジンには、既存の処理で作った**同じ材料**を渡す。型の生成直後に止まる（議事録は作らない）。
3. 結果は `output/_compare/`（git 管理外）に、表・機械可読版・材料・型として保存される。
4. 自動の採点はない。
5. 比較は、ローカルサーバーに対して **1 回ずつ**実行する（下記）。

## 比較の結果

条件:

1. 会議 2 件（A・B）、ローカルモデル 1 つ（`qwen2.5-coder-32b-instruct-mlx`、LM Studio 経由）。
2. 議事録の言語は英語。エンジンごと・会議ごとに成功した実行が 1 回。
3. 両エンジンには同じ材料を渡した（ハッシュで確認）。
4. 会議の内容はここに書かない。

| | A: 単発 | A: CrewAI | B: 単発 | B: CrewAI |
| --- | --- | --- | --- | --- |
| 材料 | チャンク要約・約 7,100 字 | 同左 | 文字起こし全文・約 22,700 字 | 同左 |
| チェックを通った | はい | はい | はい | はい |
| 実時間 | 49 秒 | 50 秒 | 90 秒 | 92 秒 |
| LLM 呼び出し | 1 | 4 | 1 | 4 |
| 検索ツール（上限 6） | 0 | 4 | 0 | 4 |
| 節の数 | 12 | 7 | 12 | 6 |

違い:

1. **粒度。** 単発は約 2 倍の節で、話題を細かく分けた。CrewAI は話題をまとめ、2 件とも、独立した節を持てない内容があった。
2. **固有の情報（一貫した傾向なし）。** 別の録画に使い回せる型が狙い。A では CrewAI の指示文に行事名と年が入り、B では単発の指示文にウェブサイトや製品の名前が入った。どちらが使い回しやすいとも言えない。
3. **時間と呼び出し。** 時間は数秒の差で、CrewAI の LLM 呼び出しは 4 倍。調査役はツールを 4 回使い、上限 6 の範囲内だった。

言えること:

1. 会議 2 件・モデル 1 つ・各 1 回（サンプリングは決定的でない）なので、勝ち負けは言えない。
2. 単純な単発版を、既定のまま残す。
3. 品質を言うには、より多くの会議が必要。

### 比較は 1 回ずつ実行すること

1. 誤って同じ LM Studio のモデルに 2 つの比較を同時に起動したところ、リクエストが重なっている間に MLX バックエンドがクラッシュした。
2. 重なった 2 つのリクエストが同時に失敗した（単独のものは成功）。
3. CrewAI エンジンは失敗を報告し、内蔵の型にフォールバックする経路に入った。
4. 上の数値は、単独で動いたリクエストのものだけ。B は、このため、2 つのエンジンが別々の実行から来ている。
